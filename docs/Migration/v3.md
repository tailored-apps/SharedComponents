# Aktualizacja do 3.0 (wersja testowa)

!!! warning "Faza testowa"
    Linia 3.0 jest wydawana jako **wersje przedpremierowe** (`3.0.0-preview.N`). API może się jeszcze zmienić przed wydaniem `3.0.0`.
    Aplikacje produkcyjne zostają przy `2.1.x` (gałąź `release/2.1`, poprawki), dopóki 3.0 nie wyjdzie z fazy testów.

Ta strona zbiera to, co trzeba zrobić **w kodzie aplikacji** przy przejściu z 2.x na 3.0.

---

## Co się zmienia

Biblioteki `TailoredApps.Shared.MediatR*` przestają zależeć od pakietu **MediatR** i korzystają z
[**ForkForward.Mediator**](https://www.nuget.org/packages/ForkForward.Mediator) — społecznościowego forka MediatR 12.5.0, ostatniej wersji
na licencji Apache-2.0 (MediatR od wersji 13 ma licencję komercyjną). Fork ma te same typy, składowe i zachowanie, ale **własną przestrzeń
nazw i własny zestaw**: `ForkForward.Mediator` zamiast `MediatR`.

Nazwy pakietów i przestrzeni nazw tych bibliotek (`TailoredApps.Shared.MediatR`, `TailoredApps.Shared.MediatR.Caching`, …) **nie zmieniają się**.

### Stripe zgłasza błędy bramki tak jak pozostali dostawcy

W 2.x dostawca Stripe przepuszczał każdy błąd API jako `StripeException` z SDK Stripe.net. Od 3.0 stosuje te same reguły co
pozostałe osiem dostawców:

| Sytuacja | 2.x | 3.0 |
|---|---|---|
| `RegisterPayment`: Stripe nie obsłużył wywołania (5xx, 408, 429, brak odpowiedzi) | `StripeException` | `PaymentGatewayException` (to `HttpRequestException`), `StripeException` w `InnerException` |
| `RegisterPayment`: Stripe odmówił (4xx — złe parametry, nieaktywna metoda płatności, zły klucz) | `StripeException` | `PaymentStatus = Rejected`, komunikat Stripe w `ResponseObject` |
| `GetStatus`: dowolny błąd, także 404 | `StripeException` | `PaymentGatewayException` |

Aplikacja, która już łapie `HttpRequestException` wokół `RegisterPayment` i `GetStatus` (zalecane od 2.0), obsługuje teraz Stripe tym
samym blokiem. Obsługa webhooków Stripe się nie zmienia.

### Odrzucone żądania nie są już logowane jako błędy

- **MediatR** — `LoggingBehavior` zapisuje żądanie odrzucone przez walidację (`ValidationException`) na poziomie **Information**:
  `Request GetProduct rejected by validation …; invalid: Id`, z samymi nazwami pól (komunikaty walidacji mogą cytować wartości wysłane przez
  klienta). Żądanie anulowane przez wywołującego (`OperationCanceledException` przy anulowanym tokenie żądania) — też Information. Każdy inny
  wyjątek handlera, jak dotąd, Error.
- **ExceptionHandling** — `ConfigureExceptionHandler()` nie oznacza już jako błędu wyjątku, któremu provider nadał status 4xx: middleware
  nie zapisuje `An unhandled exception has occurred while executing the request.` na poziomie Error i nie dodaje tagu `error.type` do metryki
  `http.server.request.duration`. Wyjątek trafia do logu na poziomie Debug, w kategorii `TailoredApps.Shared.ExceptionHandling`. Odpowiedzi 5xx
  — bez zmian.

Wcześniej jeden błąd walidacji dawał dwa wpisy Error ze stosem wywołań.

### Usunięte przestarzałe składowe

Składowe oznaczone w 2.x jako `[Obsolete]` zostały usunięte. Kompilator 2.x ostrzegał o każdym ich użyciu (CS0618).

| Usunięte | Zamiast | Po aktualizacji bez zmiany |
|---|---|---|
| `IDateTimeProvider.UtcTimeOfDaty`, `DateTimeProvider.UtcTimeOfDaty` (literówka) | `UtcTimeOfDay` | Błąd kompilacji (CS1061) |
| `FilterCollection.AddExceptionHAndlingFilterAttribute()` (literówka) | `AddExceptionHandlingFilterAttribute()` | Błąd kompilacji (CS1061) |
| `PayNowServiceOptions.ApiUrl`, klucz `Payments:Providers:PayNow:ApiUrl` | `ServiceUrl` | Kod: błąd kompilacji. Konfiguracja: **host nie startuje** z komunikatem `'Payments:Providers:PayNow:ApiUrl' is no longer read (removed in 3.0): rename it to 'ServiceUrl'.` |
| `TpayServiceOptions.ApiUrl`, klucz `Payments:Providers:Tpay:ApiUrl` | `ServiceUrl` | jak wyżej, dla Tpay |

Stary klucz konfiguracji jest wykrywany celowo: gdyby był tylko pomijany, konfiguracja sandboxu (`ApiUrl` z adresem sandboxu) po aktualizacji
łączyłaby się po cichu z produkcyjnym adresem domyślnym `ServiceUrl`.

### Nowe paczki dla minimal API

Dwie nowe, osobne paczki — nic nie zmieniają w istniejących i niczego nie trzeba migrować:

- [`ExceptionHandling.MinimalApi`](../Libraries/ExceptionHandling/MinimalApi.md) — `WithExceptionHandling()` i `WithValidation<TRequest>()`
  jako filtry endpointów, z tym samym modelem błędu co middleware i filtr MVC; zgodna z NativeAOT.
- [`EntityFramework.UnitOfWork.MinimalApi`](../Libraries/EntityFramework/UnitOfWork.MinimalApi.md) — `WithUnitOfWorkTransaction()`:
  commit po sukcesie, rollback po wyjątku albo wyniku ze statusem ≥ 400, czyli reguły filtra MVC.

### Trimming i NativeAOT

`DateTime`, `Querying`, `Email`, `Email.Models`, `ExceptionHandling`, `WebApi`, `Payments` i ośmiu dostawców HTTP (wszyscy poza Stripe)
deklarują w 3.0 zgodność z trimmingiem i NativeAOT (w Web API: na minimal API, nie na kontrolerach): opcje są wiązane kodem generowanym w czasie kompilacji, a JSON bramek serializowany przez generowane metadane. Dla aplikacji
nic się nie zmienia — treść żądań i podpisy są identyczne. Szczegóły i lista bibliotek: [Trimming i NativeAOT](../Platform/index.md#trimming-i-nativeaot).

Jedna zmiana zachowania: `CashbillHttpClient.MakeFormRequest<T>()` odczytuje odpowiedzi tylko jako typy, dla których biblioteka ma metadane
JSON — modele CashBill (`Payment`, `PaymentStatus`, `List<PaymentChannels>`) i typy wbudowane. Dla własnego typu zgłasza
`NotSupportedException`, zanim żądanie zostanie wysłane.

Poza tym biblioteki nie mają w 3.0 zmian wymagających modyfikacji kodu.

## Lista kontrolna

| # | Co zrobić | Skutek pominięcia |
|---|-----------|-------------------|
| 1 | Usunąć z aplikacji pakiet `MediatR` (i `MediatR.Contracts`), dodać `ForkForward.Mediator` — albo polegać na zależności przechodniej z `TailoredApps.Shared.MediatR` | Dwa różne zestawy typów `IRequest` / `IRequestHandler`; handlery nie są znajdowane |
| 2 | Zamienić `using MediatR;` na `using ForkForward.Mediator;` (także `MediatR.Pipeline` → `ForkForward.Mediator.Pipeline` itd.) | Błędy kompilacji (CS0246) lub niezgodność typów |
| 3 | Zamienić `AddMediatR(...)` na `AddMediator(...)`, a `MediatRServiceConfiguration` na `MediatorServiceConfiguration` | Błąd kompilacji (CS1061) |
| 4 | Podnieść **wszystkie** pakiety `TailoredApps.Shared.*` do tej samej wersji 3.0 | Mieszanie 2.x i 3.0 daje dwa mediatory w jednym procesie |
| 5 | Stripe: obsłużyć awarię przez `catch (HttpRequestException)`, a odmowę przez `PaymentStatus == Rejected`; usunąć `catch (StripeException)` wokół `RegisterPayment` i `GetStatus` | Awaria Stripe omija dotychczasowy blok `catch (StripeException)`, a odmowa nie jest wyjątkiem i zostaje nieobsłużona |
| 6 | Przejrzeć alerty i zapytania, które liczą wpisy Error lub `error.type` dla odpowiedzi 4xx | Alert na „błędy walidacji” przestaje się uruchamiać |
| 7 | Zamienić `UtcTimeOfDaty` na `UtcTimeOfDay`, `AddExceptionHAndlingFilterAttribute` na `AddExceptionHandlingFilterAttribute`, a w konfiguracji PayNow i Tpay klucz `ApiUrl` na `ServiceUrl` | Błąd kompilacji albo host, który nie startuje |

## Przykład

```csharp
// 2.x
using MediatR;

builder.Services.AddMediatR(cfg => cfg.RegisterServicesFromAssembly(typeof(Program).Assembly));

var pipeline = new PipelineRegistration(builder.Services);
pipeline.RegisterPipelineBehaviors();
pipeline.RegisterPipelineBehaviors(typeof(Program).Assembly);

public record GetProduct(int Id) : IRequest<ProductDto>;

public class GetProductHandler : IRequestHandler<GetProduct, ProductDto>
{
    public Task<ProductDto> Handle(GetProduct request, CancellationToken cancellationToken) => /* … */;
}
```

```csharp
// 3.0
using ForkForward.Mediator;

builder.Services.AddMediator(cfg => cfg.RegisterServicesFromAssembly(typeof(Program).Assembly));

var pipeline = new PipelineRegistration(builder.Services);     // rejestracja bibliotek TailoredApps — bez zmian
pipeline.RegisterPipelineBehaviors();
pipeline.RegisterPipelineBehaviors(typeof(Program).Assembly);

public record GetProduct(int Id) : IRequest<ProductDto>;

public class GetProductHandler : IRequestHandler<GetProduct, ProductDto>
{
    public Task<ProductDto> Handle(GetProduct request, CancellationToken cancellationToken) => /* … */;
}
```

Zmienia się tylko dyrektywa `using` i nazwa metody rejestrującej mediator. `IRequest<>`, `IRequestHandler<,>`, `IPipelineBehavior<,>`,
`IMediator`, `ISender`, `INotification` i pozostałe typy mają te same nazwy i składowe.

W dużym projekcie wystarczą dwa zastąpienia w całym rozwiązaniu: `using MediatR` → `using ForkForward.Mediator` oraz `AddMediatR(` → `AddMediator(`.

Działający przykład na ForkForward.Mediator — cały pipeline (walidacja, cache, retry, fallback) razem z pozostałymi bibliotekami — jest
w [aplikacji demo](../Demo/index.md).

## Na co uważać

- **Nie mieszaj obu mediatorów.** Handler implementujący `MediatR.IRequestHandler<,>` nie zostanie wywołany przez `ForkForward.Mediator.IMediator`
  i odwrotnie — to różne typy. Po migracji w aplikacji nie powinno zostać żadne odwołanie do pakietu `MediatR`.
- **Biblioteki firm trzecich oparte na MediatR** (np. własne pakiety z handlerami) trzeba przebudować na `ForkForward.Mediator`, zanim zadziałają z 3.0.
- **Zachowanie jest to z MediatR 12.5.0** — kolejność behaviorów, publikowanie powiadomień i rejestracja z assembly działają tak samo.
- `ForkForward.Mediator` to młody pakiet. Dlatego 3.0 jest w fazie testowej: sprawdź go w jednej aplikacji, zanim przeniesiesz kolejne.
- **Szczegóły błędu Stripe** (`StripeError.Code`, `Type`) są dalej dostępne: przy awarii w `PaymentGatewayException.InnerException`
  (`StripeException`), przy odmowie komunikat Stripe jest w `PaymentResponse.ResponseObject`.
- **Własne typy w `CashbillHttpClient.MakeFormRequest<T>()`** nie są już obsługiwane (`NotSupportedException`) — odczytaj odpowiedź jako
  `JsonElement` albo użyj własnego klienta HTTP.
- **Wyjątek zamieniany przez providera na 4xx** nie jest już widoczny w logu na poziomie Error. Jeśli aplikacja zamienia na 4xx wyjątki, które
  są w rzeczywistości błędami serwera, niech provider nadaje im 5xx.
