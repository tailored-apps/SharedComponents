# Upgrading to 3.0 (test phase)

!!! warning "Test phase"
    The 3.0 line is released as **pre-releases** (`3.0.0-preview.N`). The API may still change before `3.0.0`.
    Production applications stay on `2.1.x` (branch `release/2.1`, fixes) until 3.0 leaves the test phase.

This page collects what has to be done **in application code** when moving from 2.x to 3.0.

---

## What changes

The `TailoredApps.Shared.MediatR*` libraries no longer depend on the **MediatR** package and use
[**ForkForward.Mediator**](https://www.nuget.org/packages/ForkForward.Mediator) - a community fork of MediatR 12.5.0, the last version
under the Apache-2.0 licence (MediatR is commercially licensed from version 13). The fork has the same types, members and behaviour, but
**its own namespace and assembly**: `ForkForward.Mediator` instead of `MediatR`.

The package names and namespaces of these libraries (`TailoredApps.Shared.MediatR`, `TailoredApps.Shared.MediatR.Caching`, …) **do not change**.

The other libraries (Payments, EntityFramework, Email, WebApi, …) have no change in 3.0 that requires code modifications.

---

## Checklist

| # | What to do | If skipped |
|---|------------|------------|
| 1 | Remove the `MediatR` package (and `MediatR.Contracts`) from the application and add `ForkForward.Mediator` - or rely on the transitive dependency of `TailoredApps.Shared.MediatR` | Two different sets of `IRequest` / `IRequestHandler` types; handlers are not found |
| 2 | Replace `using MediatR;` with `using ForkForward.Mediator;` (also `MediatR.Pipeline` → `ForkForward.Mediator.Pipeline` and so on) | Compile errors (CS0246) or type mismatches |
| 3 | Replace `AddMediatR(...)` with `AddMediator(...)`, and `MediatRServiceConfiguration` with `MediatorServiceConfiguration` | Compile error (CS1061) |
| 4 | Raise **every** `TailoredApps.Shared.*` package to the same 3.0 version | Mixing 2.x and 3.0 puts two mediators in one process |

---

## Example

```csharp
// 2.x
using MediatR;

builder.Services.AddMediatR(cfg => cfg.RegisterServicesFromAssembly(typeof(Program).Assembly));

var pipeline = new PipelineRegistration(builder.Services);
pipeline.RegisterPipelineBehaviors();
pipeline.RegisterPipelineBehaviors(typeof(Program).Assembly);

public record GetProduct(int Id) : IRequest<ProductDto>;

public class GetProductHandler : IRequestHandler<GetProduct, ProductDto>
{
    public Task<ProductDto> Handle(GetProduct request, CancellationToken cancellationToken) => /* … */;
}
```

```csharp
// 3.0
using ForkForward.Mediator;

builder.Services.AddMediator(cfg => cfg.RegisterServicesFromAssembly(typeof(Program).Assembly));

var pipeline = new PipelineRegistration(builder.Services);     // the TailoredApps registration - unchanged
pipeline.RegisterPipelineBehaviors();
pipeline.RegisterPipelineBehaviors(typeof(Program).Assembly);

public record GetProduct(int Id) : IRequest<ProductDto>;

public class GetProductHandler : IRequestHandler<GetProduct, ProductDto>
{
    public Task<ProductDto> Handle(GetProduct request, CancellationToken cancellationToken) => /* … */;
}
```

Only the `using` directive and the name of the method that registers the mediator change. `IRequest<>`, `IRequestHandler<,>`,
`IPipelineBehavior<,>`, `IMediator`, `ISender`, `INotification` and the other types keep their names and members.

In a large project two replacements across the solution are enough: `using MediatR` → `using ForkForward.Mediator` and `AddMediatR(` → `AddMediator(`.

---

## Things to watch

- **Do not mix the two mediators.** A handler that implements `MediatR.IRequestHandler<,>` is not called by `ForkForward.Mediator.IMediator`
  and the other way round - they are different types. After the migration no reference to the `MediatR` package should remain in the application.
- **Third-party libraries built on MediatR** (your own packages with handlers, for example) have to be rebuilt on `ForkForward.Mediator` before they work with 3.0.
- **The behaviour is that of MediatR 12.5.0** - the order of behaviours, notification publishing and registration from an assembly work the same way.
- `ForkForward.Mediator` is a young package. That is why 3.0 is in a test phase: try it in one application before moving the others.

The libraries: [MediatR](../Libraries/MediatR/index.md). Upgrading from 1.x: [Upgrading to 2.0](v2.md).

## 🤖 AI Agent Prompt

````markdown
## Upgrading TailoredApps.Shared.* from 2.x to 3.0 (preview) - instructions for an AI agent

You are upgrading a .NET 10 or .NET 11 application from the TailoredApps.Shared.* 2.x packages to 3.0.0-preview. The only change that needs code modifications: the mediator.

### Registration
- Raise every TailoredApps.Shared.* package to the same 3.0.0-preview.N version
- Remove references to the MediatR and MediatR.Contracts packages; add ForkForward.Mediator where needed
- Replace builder.Services.AddMediatR(...) with builder.Services.AddMediator(...)

### What needs code changes
- using MediatR; -> using ForkForward.Mediator; (and MediatR.Pipeline -> ForkForward.Mediator.Pipeline and so on)
- MediatRServiceConfiguration -> MediatorServiceConfiguration
- The names and members of IRequest, IRequestHandler, IPipelineBehavior, IMediator, ISender, INotification do not change

### Configuration
- No new configuration keys

### Rules
- After the migration no reference to the MediatR package or namespace may remain in the solution
- Do not rename the TailoredApps.Shared.MediatR.* namespaces - they are library names, not the MediatR package
- Do not mix TailoredApps.Shared.* packages of versions 2.x and 3.0 in one application
- 3.0 is a pre-release: do not deploy it to production without an explicit decision of the application owner
````
